# Runbook

1. Verify the reviewed release SHA256 with `python3 -B install.py`; run `python3 -B -m unittest -q test_study`.
2. Use an existing private capture-volume child directory owned by the engineering account (0700). Obtain its device ID and pin it. No new storage purchase or root-filesystem fallback is authorized.
3. Bounded operation as the engineering account: `python3 -B worker.py --state /path/on/capture-volume/study-v1 --device DEVICE_ID --expected-sha256 REVIEWED_BUNDLE --seconds 45`. Duration omitted/zero runs continuously. This creates a real new prospective study; repeat only with identical reviewed source/config. Never erase it on failure.
4. Persistent installation is the owner-root installer: `python3 -B install.py --install --state /path/on/capture-volume/study-v1 --device DEVICE_ID --expected-sha256 REVIEWED_BUNDLE`. It installs only `vivameda-crypto5m-study.service`, resumes a same-pin source study, and leaves existing units unchanged. The new runtime is root-owned; the process runs as the existing engineering user. Installer refuses an existing deployment rather than rewriting it.
5. Inspect `systemctl status vivameda-crypto5m-study.service --no-pager`, then the study's `status.json`. A process being active does not prove any feed is healthy. Check capture health, per-asset stream events, source freshness, skipped reasons, storage reserve and current heartbeat. Reference adapter unavailable means no pricing/trading; this is expected and explicit.
6. Read-only report: `python3 -B report.py --state /path/on/capture-volume/study-v1`. Existing final-period performance is excluded until registered release time. Risk monitoring exists for safety and must not be used to retune the frozen version. JSON includes missing sensitivity estimates; missing is not zero.
7. Pause new virtual entries with `touch /path/on/capture-volume/study-v1/STOP` under the engineering account. Pending unfilled legs are cancelled; existing shares remain tracked to settlement. This is distinct from a daily-loss halt, which has no automatic resume and needs documented review. All current operational strategies already skip without verified contractual inputs.
8. Owner may stop this new collector alone with `systemctl stop vivameda-crypto5m-study.service`; start the same reviewed service with `systemctl start vivameda-crypto5m-study.service`. The collector records reconnect generations; existing pending intents are cancelled once on restart. No other unit should be stopped or restarted for this experiment.
9. Recovery: preserve ledger/index/capture, inspect the first exception and compare exact code/config/device. A changed pin, missing mount or integrity failure is a real stop; never replace the ledger or copy in a synthetic seed. Use a new version/study for policy changes. If storage fills, preserve records and review archival/extension before resuming.
10. Four final evaluation weeks follow the fixed 14-day development schedule. Adequate trade/data counts, calibrated probabilities and a dependence-aware comparison remain necessary; elapsed time alone does not pass a gate. Alternative-delay replay and authenticated contractual reference integration remain explicit later acceptance gates.
